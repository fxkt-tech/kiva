# 角色与主理人视频化重设计

## Goal

以“观众愿意继续看、能快速记住人、冲突与反转能被画面放大”为第一目标，采用「东方都市异闻 × 深夜推理秀」方向，重做首批演员池与唯一主理人的完整节目包装。每局固定 12 个席位，具体 Actor 从启用演员池中选择；同时保证狼人杀信息边界、行动合法性和人物决策质量不被娱乐化表达破坏。

## Background

- 当前标准局固定使用 12 个玩家席位、6 种规则身份和 2 名可选主理人；本任务中的 Actor 指具有姓名、头像、人设、说话/推理风格和声音的演员，不改狼人、预言家等规则身份。
- 12 名玩家共用 2 个基础 Edge 音色，主要靠 pitch、volume 的小幅变化区分；多名角色同时落在“冷静逻辑”“强势施压”“温和梳理”等相近轴线上，听觉和行为辨识度不足。
- 现有 12 张头像统一为月夜庄园背景的暗色二次元半身像，多数男性是黑发黑衣冷脸，轮廓、色相和构图高度接近；小尺寸座位卡上更难快速分辨。
- 两名主理人是“守夜人”和“法官”，均没有头像并使用同一基础音色；前者偏悬疑文案、后者偏规则播报。用户已明确只保留 1 名主理人。
- 当前 1920×1080 视频以两侧 12 个座位轨、中间事件/人物舞台、底部字幕为核心；主理人会显示为字幕说话者，但没有独立的视觉人格或镜头资产。
- 当前视觉主色是深黑/庄园背景/金色线框，玩家头像也使用同一暗色环境，画面统一但层级和人物色彩区分偏弱。
- 已有提示词 v2 任务正在处理场景、听众、信息边界和最低有效贡献。本任务应复用这些硬约束，把新人物风格作为其上的表现层，不能重新引入泄密、编造和只顾口头禅的问题。

## Requirements

### R1. 单一节目世界观与视觉语法

- 整体方向确定为「东方都市异闻 × 深夜推理秀」：现代人物、深夜档案馆/演播室语境，以旧纸金、冷青和朱砂红为核心色；所有玩家、主理人、头像、舞台色彩、身份标识和播报文案必须来自这套统一语法，而不是 13 个孤立的人设。
- 每名玩家至少有一个在 120px 左右头像尺寸仍可识别的视觉锚点：轮廓、发色/服装色、配饰、姿态或光线组合，不依赖姓名文字区分。
- 整体画面需在夜晚悬疑感之外提供明确的角色专属色和事件强调色，保持字幕可读性和身份信息层级。

### R2. 为视频而设计的 12 人群像

- 每局固定 12 个玩家席位，但 Actor Library 是可扩展演员池；创建对局时从全部已启用 Actor 中选择 12 个不同 Actor。Actor 一经定义，不因游戏主题、规则身份或单局内容而更换姓名、头像、人物内核或基础声音。
- 本局选中的 12 名玩家必须在姓名、年龄感、外形轮廓、主色、声音、语言节奏、推理入口、风险偏好和镜头功能上形成可比较的差异；Library 还要能发现整个演员池中的近似重复。
- 人物组合必须主动制造可观看的关系：至少包含天然对手、意外盟友、节奏调节者、观众代入位和反转潜力位，不能只是一组孤立的性格标签。
- Actor Definition 只能声明可复用的互动策略与冲突接口，不得写死其他 Actor ID 或永久关系；群像分工和核心关系必须由本局实际 12 人动态匹配。
- 每名玩家需要同时定义稳定核心、可变局势行为、标志表达和禁止过度表演项；风格不得覆盖事实、规则、当前任务与信息披露边界。
- 新角色要在好人、狼人、神职等随机身份下都能成立，不把人物性格硬绑定为某个阵营。
- 每名角色拥有自己的 LLM provider/model 配置，并在创建游戏时保存到玩家快照；规则身份和座位预设不覆盖该配置。角色不配置 `temperature` 或 `maxTokens`，由模型服务使用默认值。
- 秦川是作者在作品中的稳定化身；本轮重构必须保留名称「秦川」和稳定 ID `qin_chuan`，不能随其他 Actor 一起重命名。是否进入某局 12 人阵容完全取决于该局选择，其 Actor Definition、Rule Role 分配、可见信息、决策约束、群像分工和戏份优先级均与其他 Actor 使用同一契约。
- 首批正式演员为：秦川（全局建模/信息整合）、乔可（观众代入/直觉追问）、周序（事实记录/票型顺序）、夏弥（社交点火/拉人互动）、任野（生存反应/识别施压甩锅）、顾绫（强势审讯/正面冲突）、程雾（风险控制/划清边界）、叶忱（反共识/攻击舒服结论）、迟木（沉默观察/关键补刀）、唐梨（轻喜剧/玩笑试探）、陆燃（冲锋站边/迫使表态）、苏弦（关系分析/互保互踩）。后续允许新增 Actor，但剧本不能按主题临时改写或克隆 Actor 变体。

### R3. 单局主题作为叙事背景

- 引入独立的「剧本」库。剧本是每局选择的节目制作包，至少包含稳定 ID、名称、主题、共同背景梗概、氛围关键词、页面/视频视觉配置和背景资产。
- 第一版实现一个正式剧本「未明档案」，采用「东方都市异闻 × 深夜推理秀」方向；数据与 UI 仍按多剧本选择设计，后续可以新增其他剧本而无需修改演员定义。
- 每局在创建时选择一个剧本并保存剧本快照。本局 Actor 在不改变人物核心的前提下，把该剧本作为本局表达、类比和气氛的背景。
- 主题不能改变规则、身份、合法候选或事实边界，也不能添加 Actor Definition 中不存在的局外关系；不能要求 Actor 假装成另一套人物。
- 同一主题必须以结构化方式进入玩家 Prompt、主理人节目包装和视频标题/场景氛围，避免仅依赖游戏标题猜测。
- 角色对主题的使用应服务于当前任务和自然表达，不能每句强行复述主题词或用背景设定替代狼人杀判断。
- 剧本不定义临时职业、人物恩怨、个人前史或角色专属秘密；其背景是所有玩家共享的叙事环境，不是狼人杀事实或可用于判断身份的证据。
- 剧本与 GameSetup/Lineup 分离：Lineup 只有一份 12 席 `{seatNo, actorId, ruleRoleId}` 真相源，剧本负责叙事与呈现；选择剧本不得隐式改变 Actor 或 Rule Role 的席位分配。
- Script Author 必须从当前 Game 快照读取本局实际选中的 12 个 Actor 和本局启用的 Rule Role/规则配置，不得从全局默认首批演员或固定标准身份表推断阵容。

### R4. 唯一主理人

- 唯一主理人锁定为「闻舟」，定位为冷静的档案开启者：低沉短句、克制控场、负责翻页和收束，不替玩家分析局势或抢夺戏剧中心。
- 主理人库最终只保留 1 个启用项；所有新 Lineup/自定义阵容统一解析该主理人并保存完整快照。
- 主理人必须有独立姓名、头像、视觉符号、声音参数和完整播报风格。
- 播报需同时承担规则清晰、节奏控制、悬念推进和事件收束；短句优先，避免每个流程节点都使用同样的悬疑套话。
- 主理人不抢玩家戏份，只在阶段切换、死亡/平安夜、放逐、关键技能和终局等节点形成节目节拍。

### R5. 视频精彩程度

- 角色设计必须能被现有公共回放事件真实驱动，不依赖系统尚未拥有的面部动画或额外 LLM 旁白。
- 主理人、玩家发言、夜间行动、投票、死亡和终局应有可区分的构图/色彩/动效强调；重要反转不能只通过一行字幕表达。
- 头像设计应考虑中央大头像和两侧小座位卡两种裁切，避免关键信息贴边或只在背景中成立。
- 用一段包含玩家发言、主理人播报、夜间行动、投票和结果的代表性回放进行人工视频验收。
- Preview 和视频导出必须读取游戏保存的剧本快照，而不是当前剧本库定义，以保证创建后的游戏与历史导出视觉稳定。
- 剧本页面风格覆盖 New Game 剧本选择、首页游戏卡片、Preview 和视频导出；游戏编辑器及角色库、预设库等管理页面保持统一工具界面，不随当前剧本换肤。

### R6. 数据与 clean break

- 同步更新种子定义、运行时 `kivdb` 数据、Lineup 引用、主理人预生成语音清单、相关测试和 fixture，避免重置数据库后回退旧设计。
- 保留名称「秦川」及稳定 ID `qin_chuan`；首批其他 Actor 可以采用与最终姓名对应的新名称和 ID。
- 新头像使用项目内可复现资产路径，不依赖渲染时联网。
- New Game 流程必须显式选择一个启用剧本；剧本选择与已保存 Lineup/自定义 12 人阵容是两个独立决策。
- GameRecord schema 2、Actor/Rule Role/Lineup、Prompt v3 和 Episode schema 3 直接采用当前精确结构；旧 Character/Role/Preset 或缺字段记录明确拒绝，不做读取兼容、迁移或默认值注入。

### R7. 可恢复的 Script Author Agent

- 整集剧本创作由一个持久化 Script Author Agent 负责，但 Agent 必须把工作拆成确定性的细粒度任务，不能把法律结构、12 人完整弧线、关系线和全量发言节拍放进同一个模型请求。
- 固定任务顺序为：故事主轴、紧凑群像分工、逐角色弧线、逐关系弧线、按局部场景生成发言节拍、代码侧最终组装与校验。故事最多 4 幕，群像最多选择 6 对核心关系，每个字符串字段最多 80 字符；每个模型请求只投影当前任务必需的上下文，不累积对话历史。
- 每个子任务完成或失败后，都要把结构化工作区和完整请求记录持久化；同一输入重试时从第一个未完成任务继续，不重复已完成的故事、群像、角色、关系或节拍。
- Script Author 使用独立的模型绑定快照，不能继承第一个座位或任意玩家角色的模型配置。
- Script Author 可以读取本局真实的席位到 Rule Role 分配和完整合法轨迹，以创作具体对局的弧线、关系与节拍；这些全知信息只属于 Author，运行时 Actor 仍只接收自身 Rule Role 和当前可见事实。
- 必须保留 provider 的完成原因和 token usage。`finishReason=length` 时不能把被截断的 JSON 塞回整对象修复请求；节拍任务拆小，非节拍任务最多从原始紧凑输入重新生成一次。
- Script 页面在生成中展示 Agent 当前阶段、进度和已落盘请求；失败时展示已保留的弧线/节拍数量，并明确重试会断点续跑。
- 本次直接采用 `episode-author:v4` 请求契约与当前工作区结构，不读取、迁移或兼容旧 Author 中间态。最终可执行 Episode 快照升级到 schema 3，与 Actor/Rule Role 输入哈希和 `actor_arc` 任务语义一致。

### R8. Actor Definition v2 与双模式表演

- 术语必须彻底分开：狼人、预言家等称为「规则身份 / Rule Role」，秦川、乔可等称为「演员 / Actor」。Library 和代码不再用含混的 `role` 指代人设。
- Rule Role 只拥有阵营、能力、知识边界、行动顺序和规则显示信息；这些能力由规则引擎和 Task Spec 负责。移除可编辑的 `systemPrompt`、`actionPrompt`、默认模型等伪配置，避免自由文本与代码规则漂移。
- Actor Definition v2 不再保存一段总括式 `systemPrompt`，改为结构化的稳定表演契约：稳定核心、主要驱动力、注意入口、判断方式、互动策略、受压反应、认错/修正方式、表达节奏、修辞动作、禁止过度表演项、群像功能、冲突接口和变化边界。
- 同一 Actor Definition 必须编译出两个受限投影：`ActorRuntimeCard` 供实际玩家决策与表达，`ActorAuthorCard` 供 Script Author 分配弧线与关系。模型、声音、头像等制作字段不得进入 Script Author 的创作上下文。
- 游戏模式和剧本模式共享同一份 Actor 快照。游戏模式只使用稳定人格；剧本模式额外叠加当前场的 `EpisodeActorBrief`，但完整未来弧线、关系结局和计划胜方不得进入玩家运行时上下文。
- 玩家生成按职责拆为「决策」和「表演」：决策阶段基于可见事实、规则身份、合法选项和演员判断偏好产出结构化 `PlayerIntent`；公开发言再由表演阶段结合演员表达契约、长度预算和可选当前场剧本指引生成文本。夜间行动不做无意义的第二次表演调用。
- Script Author 只能给出戏剧目标、压力、当前弧线/关系推进和表达机会，不能替玩家预写基于未来事实的结论。玩家决策与剧本指引冲突时，规则、可见事实和当前任务始终优先。
- 本轮按 clean break 设计 Actor/Rule Role/Player 快照与 Prompt 契约，不保留旧 Character/Role Library 字段或中间兼容层；同步重写种子、fixture 和新游戏快照。

### R9. Library Studio v2

- Library 从按 JSON 类型暴露原始字段的 CRUD 页面，改为面向内容制作流程的内部 Studio：演员、剧本、节目包装、阵容、规则检查五个工作区。Actor 可新增、复制、编辑、停用；规则身份只读，不能借 Library 绕过规则实现。
- Library 必须预览真实编译结果，而不是拼接原始字段：Actor Runtime Card、Actor Author Card、最终 Player Prompt 片段、模型/声音快照、引用关系和 token 规模都从生产编译器生成。
- Actor 工作区需要同时提供单人编辑、全演员池差异矩阵、本局 12 人阵容矩阵、规则身份交叉场景、游戏/剧本双模式预览和声音 smoke test；能够发现演员同质化、身份绑定、越权信息、重复口癖和剧本覆盖稳定人格。
- Lineup 只保存座位到 Rule Role 与 Actor 的引用，删除重复的 `roleIds`/`characterIds` 和座位级模型 override；演员拥有唯一模型绑定来源。
- Library 存储通过一个深 `ContentCatalog` 模块暴露加载、校验、保存和编译接口；页面、Game 创建、诊断和种子不再分别拼接同一份定义。存储 adapter 可继续使用本地 JSON，但文件布局和写入方式不进入调用方接口。
- Script 必须成为正式可见的 Library 工作区；Presenter 归入节目包装。新 Game 只消费经过完整 catalog 校验的已启用内容，并保存不可变快照。

## Acceptance Criteria

- [ ] 首批 12 名 Actor 均有唯一名称、头像、视觉锚点、专属色、结构化人物内核、表达/判断契约和声音配置；后续新增 Actor 使用同一严格契约。
- [ ] Actor 重构后仍存在且仅存在名称为「秦川」、ID 为 `qin_chuan` 的定义；他可以像其他 Actor 一样被选中或不被选中，选中后不获得额外信息、规则能力、正确率或 Script Author 戏份优先级。
- [ ] 全部已启用 Actor 的差异矩阵能发现近似重复；任一合法的本局 12 人阵容均满足最低功能覆盖和辨识度约束。
- [ ] 新头像在中央大图和两侧 120px 级小图中均可辨识，且无明显风格漂移、构图裁切或文字伪影。
- [ ] 主理人库只有 1 个启用项，具有名称、头像、专属声音和覆盖全部播报 key 的一致文案体系。
- [ ] 新局从全部已启用 Actor 中选择且仅选择 12 个不同 Actor，不要求包含任何指定 Actor；阵容与 Rule Role 配置、剧本选择分别完成校验和快照，创建后不再回读全局演员池补位。
- [ ] 新局可明确设置主题；主题会进入玩家生成上下文与视频节目包装，但不会改变 Actor 定义、规则或事实边界。
- [x] New Game 可从启用剧本中选择「未明档案」，并与已保存/自定义 Lineup 独立组合；创建后的 Game 保存完整剧本快照。
- [ ] 剧本定义包含主题、共同背景、氛围关键词、页面/视频视觉 token 与背景资产，校验器能拒绝缺失或非法定义。
- [ ] 玩家 Prompt 将剧本明确标为“共同叙事背景、不可作为身份事实”，并在不强制复读主题词的前提下指导表达。
- [ ] Preview 和视频导出使用游戏剧本快照；修改剧本库不会改变已创建游戏的成片外观。
- [ ] New Game 剧本卡、首页游戏卡、Preview 和导出视频均能识别并呈现「未明档案」视觉；编辑器与管理页面保持全局工具主题。
- [x] 当前 GameRecord 只接受 schema 2 精确结构；旧 Character/Role/Preset 快照被明确拒绝且没有兼容分支。
- [ ] 代表性视频片段能清楚区分玩家发言、主理人播报、夜间行动、投票、死亡/平安夜和终局，并通过 1920×1080 截帧检查。
- [ ] 相关角色、主理人、预设、回放、语音、视频单测，以及 typecheck、build 全部通过。
- [x] Script Author Agent 按确定性细粒度任务完成整集剧本，单个节拍请求不超过 5 步，逐任务持久化并可从失败点续跑。
- [x] Provider 长度截断不会触发整份 JSON 修复；请求记录保留 raw output、finish reason 和 token usage，Script 页面展示实时进度与恢复信息。
