# Private Event Workflows

## 1. Scope / Trigger

Use this contract when an action spans the event log, LLM generation, Editor review, visibility projection, and director/public Preview. The event union in `src/core/events.ts` is the single payload owner.

## 2. Signatures

- Planning: `planNextDraft(input): DraftEvent | null` derives the next step only from active events.
- Editing: `applyDraftPayloadEdit(draft, edit): DraftEvent` preserves immutable payload fields.
- Confirmation: `confirmDraftAction(gameId, expectedDraftId)` forwards the
  rendered Draft ID; `gameActions.confirmDraft(gameId, expectedDraftId)` checks
  that ID while holding the game lock before appending an event.
- Auto-confirm: the Editor control receives `{ gameId, draftId, ready }` and
  schedules confirmation after `autoConfirmDraftDelayMs = 1_000` only when the
  persisted browser preference is enabled.
- Initial LLM generation: `AutoGenerateDraft` owns only the hidden submitting
  form; the visible Generation button receives forced pending state.
- Visibility: `projectVisibleEvents(events, viewerPlayerId, context)` owns player-facing disclosure.
- Playback: `compilePublicPlayback(events, players, { audience })` owns Preview inclusion.

## 3. Contracts

- Shared discussion events use faction/player visibility and may enter director Preview.
- `Game.players[].ruleRole` is immutable role truth. `role_assigned` events are private delivery records and must match that snapshot exactly; reducers and planners never reconstruct roles from notification events.
- Sealed intermediate choices use `host_only`; player LLM contexts must consume the normal visibility projection.
- Internal Editor control events may be persisted for state derivation but must be explicitly excluded by `shouldIncludeEvent` when they have no Preview scene.
- Resolution events carry structured source choices, tallies, final result, and resolution method. Renderers format this structure; they do not re-parse display text.
- Every Editor confirmation path, including automatic confirmation, carries the
  Draft ID rendered by that UI. A stale ID is a no-op; it must never confirm the
  newly planned Draft that replaced it.
- Auto-confirm applies to every Draft type. Non-LLM Drafts are ready when
  rendered; an initial LLM Draft becomes ready only after its generation record
  exists (success or failure), so generation is never bypassed.
- Initial generation keeps the Draft panel readable and interactive; do not
  cover it with a loading overlay. The Generation button is disabled and shows
  a spinner until the first generation record arrives.

## 4. Validation & Error Matrix

- Executing Player is dead or has the wrong Rule Role → reject in the server action.
- Target is dead or forbidden by the role mechanic → reject in the server action.
- Required human tiebreak is empty → reject confirmation.
- Human tiebreak is outside the tied candidates → reject the edit/confirmation.
- `expectedDraftId` differs from the current Draft ID → return the current
  record unchanged; the action may still call `continueGame`, which is a no-op
  while a Draft exists.
- Auto-confirm disabled, Draft not ready, or component/toggle changes before
  1000 ms → clear the timer and do not submit.
- Initial LLM generation pending → disable the visible Generation button while
  the hidden form owns the in-flight submission.
- Internal or sealed event reaches public Preview/LLM context → regression failure.

## 5. Good / Base / Bad Cases

- Good: faction discussion → host-only sealed choices → faction resolution with structured details.
- Base: one eligible actor still passes through the same event stages without synthetic discussion.
- Good: manual and automatic confirmation race with the same expected Draft ID;
  one confirms and the stale call leaves the next Draft untouched.
- Base: a non-LLM Draft renders while auto-confirm is enabled and confirms after
  1000 ms through the same server action.
- Good: an LLM Draft waits for generation resolution, then starts its 1000 ms
  timer; a failed generation confirms the displayed fallback Draft.
- Good: the initial LLM request runs through a hidden form while the Generation
  button alone communicates pending state and the Draft remains visible.
- Bad: filter sealed choices only in prompt string construction while leaving the underlying event faction-visible.
- Bad: confirm by `gameId` alone, allowing a delayed second request to confirm
  the next Draft after the first request has advanced the game.

## 6. Tests Required

- Planner chain test asserts every draft/event transition in order.
- Pure resolution test covers unique result and ties.
- Negative LLM-context test asserts sealed choices are absent.
- Repository regression asserts a `role_assigned` payload that differs from the immutable Player Rule Role is rejected.
- Editor/server tests assert legal candidates and reject invalid human edits.
- Server tests assert a stale expected Draft ID cannot confirm a newly planned
  Draft; UI tests assert manual and automatic paths pass the displayed ID.
- Auto-confirm tests assert the enabled/ready decision matrix and the UI exposes
  the control; type checking verifies all Draft kinds pass the shared contract.
- Draft panel tests assert initial generation has a disabled spinner button and
  no `Generating LLM draft...` overlay.
- Playback test asserts internal selection and individual sealed choices are absent while discussion and final resolution are present.
- Public visibility test asserts all private workflow events remain absent.

## 7. Wrong vs Correct

### Wrong

```ts
visibility: { kind: "faction_private", faction: "wolves" }
// Later: remove teammate votes from a prompt string manually.
```

```ts
await confirmDraftAction(gameId); // A delayed duplicate can hit the next Draft.
```

```ts
// Wrong: LLM-only completion logic leaves ordinary Drafts waiting forever.
if (generationStatus === "success") autoConfirm();
```

```tsx
<div className="absolute inset-0">Generating LLM draft...</div>
```

### Correct

```ts
visibility: { kind: "host_only" }
// Player context uses projectVisibleEvents; the sealed vote never enters it.
```

```ts
await confirmDraftAction(gameId, draft.id);
// The server compares draft.id under the game lock before confirming.
```

```ts
// Correct: all Drafts use one readiness gate and one delay.
if (enabled && ready) scheduleConfirm(draft.id, 1_000);
```

```tsx
<FormSubmitButton forcePending={generatingInitialDraft} />
```
